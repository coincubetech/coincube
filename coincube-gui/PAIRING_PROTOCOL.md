Pairing completion protocol 1 (within QR v3)

The pairing QR is v3 only, on every chain (signing identity contract §4.1, `docs/BTCB2_SIGNING_IDENTITY.md` §4). It carries `net`, the Vault's chain as its Connect network id, and the phone's proof is `HMAC-SHA256(psk, "coincube-pair-v3" || desktop_cert_fp || phone_cert_fp || net)`, which the desktop verifies with its own `net`. A phone that predates v3 refuses the code at scan; no v1 or v2 code is emitted or read. Before the proof the desktop requires the offer to be its own v3 offer for the chain of the Vault loaded now (a Bitcoin Vault and its Bitcoin Blake2b twin share a vault id, so the vault-id guard alone cannot tell them apart). After it, `SignerBinding.network` must be non-empty ("Update COINCUBE Mobile and pair again.") and equal to the offer's `net` ("Exact pairing identity mismatch; pair again.").

The stored row (`paired-phones.json`, one row per phone certificate) records the offer's `net` as `network` and `PairingComplete.capabilities` as `capabilities`, once, at pairing; they are not refreshed afterwards. A row without `network` was made before v3: it stays listed and removable, and is never used to sign on any chain ("This pairing predates network-aware signing. Pair this phone again."). Pairing a phone for another chain replaces its row and keeps the user's name for it; the pairing screen says so before the user scans.

Which rows a Vault dials is one predicate, `exact_signer_against` (shared by signing, the hardware refresh and the settings list), which takes the Vault's chain: the row's `network` must be that chain ("Paired for <label>. Pair again to use it here."), and on Bitcoin Blake2b the row's `capabilities` must hold `chain-identity-v1` and `btcb2-unified-v2` ("This phone's COINCUBE Mobile needs updating before it can sign on Bitcoin Blake2b."). A refused row is not dialled; the settings list and the signer list show the refusal for this Vault's rows. Bitcoin Blake2b has no other Wi-Fi gate.

Every signing request's `PresentSession.session.network` is the Vault's chain, and every `PartialSignature.network` must equal it. An empty or different value is discarded before the signature is decrypted, verified or merged: "Your signature wasn't accepted and nothing was broadcast from it. Update COINCUBE Mobile and pair again." (empty) or "… The signature COINCUBE Mobile returned is for a different network. Pair again." (different).

The QR PSK, TLS identity, chain, exact selected xpub/origin and descriptor commitment checks precede staging. PairingComplete.completion_protocol must equal 1. Pong is exclusively liveness. Old peers must update both applications and create a fresh offer.

Desktop has three durable journal states:

- `provisional`: candidate hidden, exact prior row visible, cancellable and automatically reversible.
- `decided`: candidate hidden, exact prior row visible, irreversible by automatic cleanup or cancellation.
- `completed`: candidate visible, entered only after the matching FINISHED acknowledgement and a durable completion write.

Desktop stages candidate/prior under a fresh local UUID, sends ACCEPT and waits for PREPARED. Phone stages candidate/prior under a separate local 256-bit nonce. Desktop writes its hidden candidate and sends COMMIT; phone writes its hidden candidate and replies COMMITTED. Both writes are acknowledged, but cancellation can still win. Desktop then writes `decided` inside PairingRun's cancellation lock. That write is the cancellation linearization point. FINISH is sent only after it succeeds. Desktop exposes nothing new while waiting for FINISHED. After FINISHED, it durably writes `completed` and reports success.

Every desktop automatic rollback, including Drop after task abort, reads current durable journal ownership and state. Only the matching provisional transaction may roll back. Every postdecision error (EOF, timeout, unexpected frame, storage failure), future drop or restart leaves the decided record hidden. No second write is needed to hide it. Failure to record completion leaves the decided journal in place. Explicit re-pair is recovery; user unpair/rename supersedes journal authority. Older `finished` journals cannot prove final acknowledgement and are conservatively treated as decided/hidden, requiring re-pair.

Phone accepts FINISH as the coordinator's durable decision. After the local finish write succeeds, socket/acknowledgement failure or cancellation cannot automatically roll it back. PairingStore also refuses rollback of a finished transaction, including delayed cleanup after a storage implementation has completed its write. Explicit unpair still revokes it. A failed acknowledgement is reported as uncertain completion requiring re-pair. The phone cannot know whether its final acknowledgement reached desktop.

Every phone attempt has one local cancellation owner independent of peer certificate and wire transaction ID. Waiting UI cancellation/disposal, stop, dispose and pause/detach revoke and drain unfinished handlers and their storage operations. Teardown closes pending sockets before awaiting cleanup; old attempts cannot register connections after teardown. Resume does not resume an unfinished pairing. Pause/detach preserve the intended sticky listener port, while full stop resets it. Temporary TLS trust derives only from live pending records. Serialized listener updates remove it on all exits; stale owners cannot remove a replacement's trust. Successful pairing trust comes from the durable store.

All post-staging protocol failures are terminal and require a fresh user-approved offer, never automatic redial with a consumed offer. Every journal mutation checks local ownership. Peer-supplied transaction IDs sequence messages but confer no journal authority. Public store reads mask hidden candidates with the exact prior row. Existing completed prior bindings remain usable until explicit user revocation.

This is not universally atomic distributed commit. FINISH or FINISHED may be lost. The phone may retain a completed row while desktop retains a hidden decided row. Desktop may crash after its local completion write but before returning success; that write follows a received FINISHED. Recovery is explicit re-pair when transport/storage are available. Persistent storage errors may prevent provisional rollback; unreadable journals fail closed, and unfinished journals mask candidates. The model relies on atomic file replacement and durable storage acknowledgements; physical corruption or loss of a journal is outside it. Host Flutter tests inject platform storage/authentication and do not prove physical iOS/Android durability under power loss.

Unpair propagation

Removing a pairing takes effect locally at once on either side; the other side is told with an `Unpaired` frame over the pinned mutual-TLS channel and removes its own record without asking the user (the frame only ends a pairing, which either side can already do alone). Desktop removal queues a `pending_unpairs` notice in `paired-phones.json`; the Pair panel (every 3 s while open) and the hw refresh loop deliver it once the phone is reachable, for up to 14 days. Pairing the same phone again drops the notice at staging. The phone only listens, so a phone removal is sent on an open connection if there is one, and otherwise the phone remembers the desktop (`.revoked`, 30 days, at most 32), keeps its certificate in the TLS trust set and answers its next connection with `Unpaired` alone, reading nothing. A desktop that understands the frame never reconnects; one still connecting after three tells predates `Unpaired`, so the phone refuses it at the TLS layer again and it sees the phone as offline. The desktop learns it from the signer's reader on the signing screens and from a Ping probe in the Pair panel, then removes exactly the row that connection was made for. Like a removal made on the desktop, that supersedes any pairing journal for the phone, including a decided one left by a lost FINISHED. Peers without `Unpaired` support behave as before: removal is local only.

PairingStep ACCEPT carries `desktop_name`, which the phone lists the pairing under. The QR's `svc` names the phone itself; phones that stored it as the desktop's name show a generic label until the desktop pairs again.

Pairing code (display only)

The waiting screen shows this computer's pairing code above the QR. The mobile side of the comparison is planned (Mobile V3 Phase 1, slice M14) and not built: once it is, COINCUBE Mobile shows the same code before the user pairs and asks whether the two match. Today's COINCUBE Mobile shows the same eight characters as "Desktop ID", in lower case and ungrouped, and asks nothing.

The code is a display of a value both sides already hold: the desktop certificate fingerprint, `certFp` (SHA-256 of the certificate DER, 64 lowercase hex characters), which the QR has always carried and the phone already checks against `cert`. Format 1: the first 8 characters of `certFp`, in upper case, as two groups of four separated by one space (`A1B2 C3D4`). The full code is all 64 characters in the same style, 16 groups of four; the short code is its first two groups. Desktop labels it "This computer's pairing code". It is never derived from the phone's fingerprint, which the same screen shows on a separate line beside the QR ("Scan with COINCUBE Mobile on phone ...") to name the phone being paired.

A QR from a desktop that shows the code carries one more key, `"pc": 1` (the format number). The phone is to ask the user to compare only when it reads a format it knows; without the key, or with another value, it pairs as before. A phone that predates the key ignores it, because its parser reads the keys it names and no others. `PairingOffer`, the proof, the listener, expiry and the completion exchange are unchanged, and `pc` is not an input to the proof.

Pairing safety does not rest on the comparison. The certificate pin and the proof decide whether a pairing completes, as before, and neither side waits for or records an answer. What a match is worth: it rules out the phone having read some other computer's QR by accident. It does not rule out a deliberately substituted QR, for two reasons. Whoever can replace the QR can replace every field in it, `pc` included, and removing `pc` removes the question. And the code is 32 bits: a substituted QR can keep `pc` and carry a certificate chosen so that its fingerprint starts with the same eight characters (about 2^32 tries, offline), which the full fingerprint, shown and copyable on this screen, does not make harder. The comparison is a convenience for the user and must not be treated as a control. A different code means the phone read another QR, so the place to cancel is the phone.

The shared test fixture is `src/phone_signer/fixtures/pairing_code_v1.json` (formatting and QR parsing only).
