# Imported password-v3 restore backend contract

`services::recovery::imported_restore_v3::fetch_and_restore_password_v3` is the narrow, non-UI entrypoint for a clean-device imported Bitcoin wallet restore. It accepts an unlocked target Cube, its authenticated Connect client, the password, and a cancellation/session predicate. The password and decrypted phrases never enter the cloneable installer restore enum. It returns public record/revision identities and a point-in-time checkpoint receipt. That receipt is **not** signing authority.

The caller must not treat a public-only v2 Kit as a local-key restore. A v3 download is admitted only after ciphertext SHA-256, password envelope, Cube UUID, operation ID, wallet/chain/policy/account identity, record IDs/revisions, and current Connect generation/commitment validate. The restore coordinator also checks the live Cube identity, network, unlock session, Duress state, and conflicting local wallet/key state. Unsupported or unavailable Connect responses fail closed.

Restore rejects a platform without a verified device keystore anchor adapter before creating an operation lock, durable intent, or public wallet. The production anchor adapter currently supports macOS; Linux and Windows must fail before local mutation until their own verified adapters exist.

## Durable sequence and restart behavior

1. Download and decrypt v3, then recheck current Connect status after the KDF. Preflight the target Cube and local state.
2. Fsync a non-secret per-operation restore intent before any public wallet mutation. A preexisting key root without that intent conflicts, even when the operation ID matches. The intent blocks the legacy signer before any key read. An exact retry reuses it; a partial create-new write is discarded only under its stable operation lock, while a different intent conflicts.
3. Install public wallet/config/address high-water marks through the existing crash-resumable import journal, using `PasswordV3` so the public half cannot mark Recovery Kit backup complete. Recheck Connect status. The old synchronous local-key signer has no v3 keys to use at this point.
4. Reread the installed wallet and its address state. Reseal the exact v3 record IDs and revisions to this device, then commit the full signer set plus checkpoint tuple into one device-anchored manifest transition with `ready=false`. A crash before its Pending anchor is safely discarded by the existing batch protocol; after Pending, the existing recovery either authenticates the complete candidate or refuses it. An exact retry authenticates all records and resumes without changing their identities. A conflicting signer set fails closed.
5. Recheck Connect immediately before and after changing the anchored binding to `ready=true`; verify the public wallet again, then remove and sync the restore intent. A crash before intent removal leaves signer use blocked and can be retried. No setting or cached descriptor alone authorizes signing or declares the v3 backup complete.

Ordinary single-key and batch admission take the same per-operation restore lock before the repository lock and refuse a durable restore intent, even if the device anchor currently authenticates an empty, unbound manifest. This prevents the Keys UI's Add recovery words path from filling the crash window between first anchor creation and restored-binding publication. Revocation cleanup can then retire the empty inventory against a later inactive Connect epoch and clear the intent. Only after that clearance may ordinary admission proceed.

The existing `LocalKeyRepository::sign` refuses any restored binding. `sign_restored` verifies the exact authenticated local binding and current owner Cube/checkpoint before and after signing; the signed PSBT remains private in `RestoredSignature`. `release_after_recheck` checks both again immediately before yielding it for persistence or broadcast. The caller must use that release path and perform the persistence/broadcast immediately. Offline, missing, tombstoned, replaced, stale, or mismatched states refuse signing and release.

After revoking a restored checkpoint on Connect, the owner must call `LocalKeyRepository::release_restored_after_revocation` before deleting the import or rotating its local keys: **remote DELETE → release → existing `remove_cube_import`**. This backend method serializes with restore admission under the operation lock and requires the exact owner Cube UUID/network and a strictly later inactive checkpoint epoch. For a completed restore it retires **all** restored key records together with the binding in one device-anchored transition. For an interrupted admission with a durable intent and either a staged or ready binding, it matches the intent to the anchored binding, retires the keys and binding through the same anchor, then removes and syncs the intent. If revocation happened before any key inventory was created, it proves both the key root and device anchor absent before clearing the intent. A changed or missing public wallet does not block safe key retirement; the existing owner-checked removal transaction still reconciles public wallet state. Clearing only the binding would expose those keys to the legacy offline signer. An interrupted pending-anchor transition or a crash before intent removal is retried under the same lock; owner deletion follows only after the authenticated empty inventory and intent cleanup are complete.

If revocation occurs before the public import attachment or the first device anchor exists, call `services::recovery::imported_restore_v3::release_revoked_password_v3_intent` with the original Cube UUID and operation ID. It holds the same restore operation lock, checks the unlocked local Cube and Duress state, and requires a strictly later inactive checkpoint for that exact Connect Cube and network. It accepts only an absent key root or a root containing canonical, scoped, empty first-provision manifest files, with the device-only anchor account absent. Unexpected files, ciphertext, an existing anchor, or an ambiguous local owner stop cleanup. It removes the empty root before syncing intent removal; either crash prefix can be retried. This path never decodes a signer key from the intent.

Connect status reads cannot atomically reserve a server epoch through local signing or Bitcoin broadcast. A revocation can occur after the last status response. The caller must retain cancellation and session checks, and no code may claim a stronger guarantee without an API protocol change. This backend service does not wire P-Restore UI or ordinary Send; those consumers must call this contract and preserve its fail-closed release boundary.
